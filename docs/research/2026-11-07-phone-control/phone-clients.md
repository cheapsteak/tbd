# Phone client options for controlling TBD sessions

A static web app added to the Home Screen (a PWA) can do everything the phone client needs on iOS 17 and later. It can show a session list and transcripts, send messages, and answer prompts. It can get push notifications without an Apple developer account, and it has every Web Crypto primitive an end-to-end design needs. Four limits shape the design. First, iOS shows no action buttons on web notifications, so answering a prompt always opens the app. Second, every push must show a visible notification. Third, the app gets no background time, so it reconnects and catches up on resume. Fourth, the app's origin is its trust boundary: whoever serves the JavaScript can read the keys. So the client must not come from the relay. It should come from a static origin built from the public repo, and that origin should hold nothing else. The laptop itself can send Web Push straight to Apple's push service over outbound HTTPS, encrypted to the phone, so the relay never touches notifications. A native iOS app would add lock-screen approve and deny buttons. But it needs a paid developer account and an owner for review and upkeep. Its APNs signing key also forces a central push gateway, which TBD's no-hosted-backend rule forbids. Chat apps (Telegram, Slack, Discord) need no client code and deliver push for free. But the platform reads every message, and prompt answering is limited to small buttons. The recommendation is a dependency-light PWA on a dedicated static origin, with the laptop as push sender.

Sources accessed 2026-11-07. Claims marked **(unverified)** could not be confirmed from a primary source. Library sizes were measured for this report. The method is under [Rendering](#4-rendering). A sibling report, [orca.md](orca.md), covers one existing product's phone app.

## 1. A PWA (web app added to the Home Screen)

### 1.1 iOS Web Push

- **Availability** – Web Push works on iOS and iPadOS 16.4 and later, only for web apps added to the Home Screen. The site needs a manifest whose `display` is `standalone` or `fullscreen`. ([WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/); [MDN compat data for `PushManager`](https://github.com/mdn/browser-compat-data/blob/main/api/PushManager.json), first iOS version 16.4.) In a plain Safari tab on iOS the `Notification` interface is undefined ([MDN compat data for `Notification`](https://github.com/mdn/browser-compat-data/blob/main/api/Notification.json)).
- **iOS 26 makes install easier** – "By default, every website added to the Home Screen opens as a web app," with or without a manifest ([WebKit: Safari 26 beta](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/)). A manifest is still needed for icons and for Web Push.
- **Permission needs a gesture** – The app must ask in response to a tap. Apple says to "call the push subscription method immediately from the gesture's event handler code" ([Apple: Sending web push notifications in web apps and browsers](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)).
- **No Apple account** – "You don't need to join the Apple Developer Program to send web push notifications" (same Apple page). The push uses the standard Web Push protocol with VAPID keys. Firewalls must allow `https://*.push.apple.com` (same page).
- **Every push must show a notification** – "Safari doesn't support invisible push notifications. … If you don't, Safari revokes the push notification permission for your site" (same Apple page). WebKit says the same thing: "Violations of the `userVisibleOnly` promise will result in a push subscription being revoked" ([WebKit: Meet Web Push](https://webkit.org/blog/12945/meet-web-push/)). Neither source says how many violations Apple tolerates. So push cannot be used as a silent "wake up and sync" signal.
- **Delivery limits** – The payload limit is 4 KB. If the device is offline, Apple stores a notification for up to the `TTL` you set, at most 30 days, and it stores a limited number per device. The `Urgency` header can be `very-low`, `low`, `normal` or `high`. The VAPID JWT may not expire more than one day ahead, and Apple asks senders not to refresh it more than once an hour. (All from the [Apple page](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).)
- **Declarative Web Push (iOS 18.4 and later)** – The push payload is JSON (`"web_push": 8030`, a `notification` with a `title` and a `navigate` URL), and the system shows it without running a service worker. "Unlike with original Web Push, there is no penalty for service workers failing to display a notification" ([WebKit: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)). A service worker can still change the content if one is installed. This removes the revocation risk on iOS 18.4 and later.
- **No action buttons** – Safari on iOS supports neither the `actions` option nor `requireInteraction` ([MDN compat data for `showNotification`](https://github.com/mdn/browser-compat-data/blob/main/api/ServiceWorkerRegistration.json); [for `Notification`](https://github.com/mdn/browser-compat-data/blob/main/api/Notification.json)). A user cannot tap "Allow" on a permission prompt from the lock screen. The tap opens the web app, which then shows the prompt. The `navigate` option, from Safari and iOS 18.5, can send that tap straight to the right session (same compat file).
- **Badge** – `navigator.setAppBadge()` works in Home Screen web apps from iOS 16.4 ([MDN compat data for `Navigator`](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json)). The badge can count sessions waiting for the user.
- **Reliability in practice (unverified)** – Apple publishes no delivery-rate or latency figures for web push. Treat a push as a strong hint, not a guarantee. The app should always rebuild state from the relay when it opens.

### 1.2 Background limits and resume

- **No background sync** – Safari supports neither Background Sync nor Periodic Background Sync ([MDN compat data for `SyncManager`](https://github.com/mdn/browser-compat-data/blob/main/api/SyncManager.json) and [`PeriodicSyncManager`](https://github.com/mdn/browser-compat-data/blob/main/api/PeriodicSyncManager.json)). The only background entry point is a push event, and that must show a notification.
- **WebSockets die in the background (Apple does not document this)** – Developers report that iOS kills a page's WebSocket soon after the app leaves the foreground. Sometimes no `close` event fires, so the socket looks open but is dead ([Flarum issue 4588](https://github.com/flarum/framework/issues/4588); [Apple Developer Forums thread 696310](https://developer.apple.com/forums/thread/696310)). One native companion app chose to drop its own connection 30 seconds after backgrounding ([orca.md](orca.md)).
- **What the client should do on resume** – Listen for `visibilitychange` and `pageshow` ([MDN: Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)). On resume, throw away the old socket, open a new one, and ask for everything after the last event cursor the client saw. The relay or the laptop must keep a short backlog for this. Design every message so a duplicate is harmless.

### 1.3 Storage and keys

- **The 7-day storage cap does not apply** – Safari deletes a site's script-writable storage after seven days of Safari use without a visit. WebKit says: "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use. … We do not expect the first-party in such a web application to have its website data deleted" ([WebKit: Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). The counter counts days the app is used, so an app that sits unused for a long stretch still has a theoretical exposure (unverified in practice).
- **Quota and persistence** – From iOS 17, a Home Screen web app gets the same quota as the site in a browser. WebKit grants `navigator.storage.persist()` "based on heuristics like whether the website is opened as a Home Screen Web App" ([WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). The client should call `persist()` once after install.
- **Safari and the Home Screen app do not share storage** – A WebKit bug open since 2018 reports that Home Screen apps and Safari have separate storage ([WebKit bug 181849](https://bugs.webkit.org/show_bug.cgi?id=181849)). WebKit also says a user can install several copies of one web app "and give them different identities" ([WebKit iOS 16.4 post](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)). Apple does not document this as a contract (unverified as policy), but every source agrees. This matters for pairing (see 1.5).
- **CryptoKey objects can be stored in IndexedDB** – The Web Crypto spec makes `CryptoKey` serializable and expects authors to store keys in IndexedDB ([W3C Web Cryptography, sections 5.2 and 13.5](https://w3c.github.io/webcrypto/)).
- **Stored X25519 keys break on Safari today** – An open WebKit bug, filed April 2026, reports that a non-extractable X25519 key put into IndexedDB comes back as `null` in Safari 26.4. The reporter says non-extractable AES-GCM keys work ([WebKit bug 312279](https://bugs.webkit.org/show_bug.cgi?id=312279)). A WebKit pull request was linked in October 2026, but the bug was still open. Nobody reported on Ed25519 or P-256. Assume P-256 ECDH, ECDSA and AES-GCM keys work, and test on a device before relying on them (unverified).
- **Non-extractable does not mean unusable** – `extractable` only controls `exportKey()` and `wrapKey()` ([MDN: CryptoKey](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey)). Any script running on the same origin can still use a stored key to decrypt or sign. So the flag stops key copying, not key misuse by hostile code on the origin. This is why the origin question in 1.7 and 1.9 matters.

### 1.4 Web Crypto on iOS Safari

The table below gives the first version with support, from [MDN browser-compat-data for `SubtleCrypto`](https://github.com/mdn/browser-compat-data/blob/main/api/SubtleCrypto.json). The unprefixed `crypto.subtle` arrived in Safari and iOS 11. Before that, Safari had only a `webkit`-prefixed version. Web Crypto also needs a secure context, which GitHub Pages provides over HTTPS.

| Primitive | Safari and iOS Safari | Chrome and Chrome Android |
|---|---|---|
| ECDH P-256 | 11 | 41 |
| HKDF | 11 | 41 |
| AES-GCM | 11 | 37 |
| X25519 | 17 | 133 |
| Ed25519 | 17 | 137 |

Compat data lists ECDH, HKDF and AES-GCM support at the method level (`deriveBits`, `deriveKey`, `encrypt`), not per algorithm. X25519 and Ed25519 have their own entries. The practical floor for a modern design is iOS 17. P-256 with HKDF and AES-GCM works on every iOS version that has Web Push. Workers, including service workers, have had `crypto.subtle` since Safari 11.

### 1.5 QR pairing

- **Camera inside the web app works** – `getUserMedia` has been in Safari since iOS 11. It failed in Home Screen apps until iOS 13.4, when WebKit fixed it ([WebKit bug 185448](https://bugs.webkit.org/show_bug.cgi?id=185448)).
- **No native barcode API on iOS** – `BarcodeDetector` is behind a flag in Safari 17 and later. It is on by default in Chrome Android 83 and later ([MDN compat data for `BarcodeDetector`](https://github.com/mdn/browser-compat-data/blob/main/api/BarcodeDetector.json)). On iOS the app needs a JavaScript QR decoder. jsQR is about 57 KB gzipped (see section 4), so load it only on the pairing screen.
- **Scanning with the Camera app lands in Safari, not in the installed app** – iOS Safari supports neither `launch_handler` nor `protocol_handlers` ([MDN compat data, manifest `launch_handler`](https://github.com/mdn/browser-compat-data/blob/main/manifests/webapp/launch_handler.json), [`protocol_handlers`](https://github.com/mdn/browser-compat-data/blob/main/manifests/webapp/protocol_handlers.json)). Nothing documented sends a scanned URL into an installed web app (unverified as an absolute). Because storage is separate (1.3), a secret in a `#fragment` that Safari opens is not visible to the installed app. Whether "Add to Home Screen" carries the current URL and fragment into the new app is also unverified.
- **The fragment idea is still sound for the secret's path over the network** – A URL fragment is never sent in the HTTP request, so a `#pair=…` secret does not reach GitHub Pages logs. The problem is only which storage receives it.
- **Suggested flow** – The laptop shows two codes. The first is a plain install URL with no secret, which the user opens with the Camera app and adds to the Home Screen. The second is the pairing payload, which the installed app scans with its own camera view. A short typed code is the fallback. On Android, one QR works, because Chrome can open the link in the installed app (unverified) and has `BarcodeDetector`.

### 1.6 Android

- **Install and push just work** – Chrome on Android supports Web Push in an ordinary tab, from Chrome 42 ([MDN compat data for `PushManager`](https://github.com/mdn/browser-compat-data/blob/main/api/PushManager.json)). Installing creates a WebAPK, so the app appears in the launcher and in Android's app settings ([web.dev: WebAPKs on Android](https://web.dev/articles/webapks)).
- **Better than iOS on two points** – Chrome Android supports notification action buttons ([MDN compat data for `showNotification`](https://github.com/mdn/browser-compat-data/blob/main/api/ServiceWorkerRegistration.json)), so "Allow" and "Deny" can live on the notification. It also has `BarcodeDetector`.
- **Crypto** – X25519 from Chrome 133 and Ed25519 from Chrome 137 (table in 1.4).

### 1.7 Who serves the client code

End-to-end encryption protects data from the relay only if the relay cannot change the code that holds the keys.

- **The relay serves the page** – Then the relay can serve JavaScript that reads the keys and sends them anywhere. A compromised or malicious relay defeats the encryption. This holds even when each user deploys their own relay, because the relay is then trusted with both the data and the code. That is the setup end-to-end encryption exists to avoid. Do not do this.
- **GitHub Pages, built from the public repo** – Trust moves to GitHub, to everyone who can merge to the deploy branch, and to every page on the same origin (1.9). For TBD, "GitHub Pages serves it from `main`'s `docs/` folder, so merging is the deploy" ([session deep-links spec](../../specs/2026-10-25-session-deep-links-design.md)). The relay then sees only ciphertext and metadata. An attacker must compromise the code origin, not just the relay.
- **The browser cannot pin a version** – A service worker cannot freeze the app. The browser re-checks the worker script on navigation, and it bypasses the HTTP cache once a registration's last check is more than 86,400 seconds old ([W3C Service Workers, "stale" registration](https://w3c.github.io/ServiceWorker/)). Subresource Integrity can pin scripts that the page loads, but nothing pins the top-level HTML. A bad commit reaches each user the next time they open the app, or at most about a day after that.
- **The industry knows this gap** – Meta built Code Verify for WhatsApp Web because "a web app is usually served directly to users, without a third party reviewing and auditing the code." It uses Cloudflare as a third party that holds hashes of the expected JavaScript ([Meta Engineering: Code Verify](https://engineering.fb.com/2022/03/10/security/code-verify/)). TBD cannot rely on a browser extension for this. The honest mitigation is a small, readable client that is easy to audit, protected deploys, and the option to self-host.
- **Practical hardening** – Vendor every dependency into the repo, with no CDN, because a CDN is one more party that can change the code. Use a strict Content Security Policy in a `<meta>` tag, since GitHub Pages cannot set response headers (unverified as a GitHub statement). A `<meta>` policy "does not support all CSP features" ([MDN: CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)). `script-src 'self'` with no inline script blocks injected scripts. `connect-src` cannot list each user's relay, because the page is shared, so it cannot be a strong defense against data leaving the page.
- **A native app does not escape this** – App Store binaries are signed and reviewed, but App Review is not a security audit. Users still trust whoever publishes the app.

### 1.8 Who sends the push, and can it be end-to-end encrypted

- **Web Push payloads are already end-to-end between sender and phone** – RFC 8291 gives "confidentiality and integrity for messages sent from an application server to a user agent," secured "against inspection, modification, and forgery by a push service" ([RFC 8291](https://www.rfc-editor.org/rfc/rfc8291)). It uses ECDH on P-256, HKDF and the `aes128gcm` content coding. Google's guide says the same: encryption "prevents the push service from being able to view the data you're sending" ([web.dev: push notifications overview](https://web.dev/articles/push-notifications-overview)). Whoever encrypts, the sender, can read the payload.
- **What the push service still sees** – "The timing and length of communication cannot be hidden from the push service." It also sees "which application server is talking to which user agent" (RFC 8291, Security Considerations). The [VAPID](https://www.rfc-editor.org/rfc/rfc8292) JWT carries a `sub` contact claim, so use a non-identifying value.
- **The laptop should be the sender** – Sending a push is one outbound HTTPS POST to the endpoint in the phone's subscription ([RFC 8030](https://www.rfc-editor.org/rfc/rfc8030)). NAT does not block outbound HTTPS. The phone hands its subscription (endpoint, `p256dh`, `auth`) to the laptop over the encrypted pairing channel. The laptop keeps the VAPID private key and posts encrypted pushes to Apple or Google directly. The relay never sees the subscription or the notification. Apple's CryptoKit has every primitive this needs, which are P-256 key agreement, HKDF, AES-GCM and ES256 signing ([Apple: CryptoKit](https://developer.apple.com/documentation/cryptokit)).
- **When the laptop sleeps, nothing is sent** – That is acceptable, since a sleeping laptop has no session that needs the user. If TBD ever wants a "laptop went offline" alert, the relay would need a sender role. The laptop could hand it a pre-encrypted message and a VAPID JWT good for up to a day. This is optional and adds trust in the relay.
- **One VAPID key per subscription** – Calling `subscribe()` with a different `applicationServerKey` while a subscription exists fails with `InvalidStateError` ([W3C Push API](https://w3c.github.io/push-api/)). A phone paired with two laptops therefore needs both laptops to share one VAPID key pair. For example, the phone could generate the pair and give the private key to each laptop over the encrypted channel.
- **Lock-screen text is the real leak** – Apple cannot read the payload, but anyone holding the phone can read the notification. Keep the default text short, such as "acme-api: needs approval". Let the user hide session names.

### 1.9 One GitHub Pages origin for every TBD user

- **Users do not share storage** – Storage lives on each device, per origin. On iOS it is also per Home Screen install (1.3). Two TBD users on two phones never see each other's data, even though their apps have the same origin.
- **Users cannot push to each other** – A sender needs both the phone's subscription and the matching VAPID private key. User A's laptop has neither for user B's phone.
- **The trust boundary is the whole origin, not the `/tbd/` path** – Every project site of a GitHub account is served at `<owner>.github.io/<repository>` ([GitHub Docs: About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)). So `cheapsteak.github.io/tbd/` is the same origin as every other Pages site of that account. `github.io` is on the [Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat), which isolates one account from another. It does nothing inside one account. A service worker's scope does not partition IndexedDB. Any Pages site on that account could read the TBD client's storage and use its keys.
- **The origin is permanent once users pair** – Storage, the push subscription and the Home Screen install are all bound to the origin. Moving the client later means every user reinstalls and pairs again. Choose the origin before the first release.
- **A dedicated origin fixes the boundary** – Two options keep the client's origin to itself. One is a GitHub organization whose only Pages site is the client, giving `<org>.github.io`. The other is a custom domain on GitHub Pages. Neither is a backend the maintainer runs, since GitHub hosts the static files.
- **Users can fork** – A user can fork the repo and turn on Pages. Their client then lives at `<their-account>.github.io/<repo>/`, and trust moves to their own account. TBD would need a setting for the client URL that the pairing QR points to. Fork users must pull updates themselves, and their own other Pages sites share that origin.

## 2. A native iOS app

- **Cost** – The Apple Developer Program costs $99 a year ([Apple Developer Program](https://developer.apple.com/programs/)).
- **Push needs the paid program** – Apple's capability table lists Push Notifications for Apple Developer Program and Enterprise members, and not for a free Apple Account ([Apple: Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)).
- **Free provisioning is not a distribution path** – With a free Personal Team, "You can register up to 10 App IDs, which expire after 7 days," up to 3 devices that also expire after 7 days, and "up to 3 apps per device" ([Apple: Developer account overview](https://developer.apple.com/support/compare-memberships/)). There is no push. Users would rebuild from Xcode every week and get no notifications, which defeats the point.
- **TestFlight** – Up to 100 internal testers and up to 10,000 external testers. The first build for external testers must pass App Review, and a public link can invite people ([Apple: TestFlight](https://developer.apple.com/testflight/)). Each build expires after 90 days ([App Store Connect Help: TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)). TestFlight could be the whole distribution channel for an open-source project, but it still needs a paid account and steady uploads.
- **App Review risks** ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)):
  - **2.1 App Completeness** – Reviewers need "an active demo account or fully-featured demo mode, plus any other hardware or resources that might be needed … (such as login credentials or a sample QR code)." A client that is useless without a paired Mac running TBD needs a built-in demo mode.
  - **4.2 Minimum Functionality** – An app must be "beyond a repackaged website." A thin wrapper around the PWA would be at risk.
  - **4.2.3(i)** – "Your app should work on its own without requiring installation of another app to function." A companion app is exposed here. The precedents below show Apple accepts this pattern, but the rule can still be cited in a rejection.
  - **4.2.7 Remote Desktop Clients** – An app that "acts as a mirror of specific software" must connect only to a user-owned computer, and "both the host device and client must be connected on a local and LAN-based network." A transcript client renders native views rather than mirroring a screen, so this rule likely does not apply. That is a judgment, not an Apple statement (unverified). A reviewer who reads it the other way would block internet use.
  - **2.5.2** – Apps may not download code that changes their features. The agents run on the Mac, so a client that only sends text and choices should be clear of this rule.
- **Precedent: apps that control a computer over the internet are on the App Store**:
  - **Happy** – An MIT-licensed Claude Code and Codex client with end-to-end encryption and a relay server ([GitHub: slopus/happy](https://github.com/slopus/happy); [App Store](https://apps.apple.com/us/app/happy-codex-claude-code-app/id6748571505)).
  - **The Claude app** – With Remote Control, the Claude iOS app drives a Claude Code session on the user's machine. The local process "makes outbound HTTPS requests only and never opens inbound ports," and traffic goes "through the Anthropic API over TLS." It is not end-to-end encrypted. "The session transcript … is stored on Anthropic servers" ([Claude Code docs: Remote Control](https://code.claude.com/docs/en/remote-control)).
  - **SSH clients** – [Termius](https://apps.apple.com/us/app/termius-modern-ssh-client/id549039908) and [Blink Shell](https://apps.apple.com/us/app/blink-shell-build-code/id1594898306).
- **The APNs key forces a central push service** – APNs provider keys are team-scoped, covering every app of the team in one environment, or topic-specific. "This key must remain private to prevent anyone else from generating those tokens" ([Apple: Establishing a token-based connection to APNs](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)). Each user's laptop or relay cannot hold that key without handing every user the power to sign pushes for the app. So one party must run a push gateway that holds the key. Happy runs `happy-push-server`, a Cloudflare Worker that "delivers push notifications via APNs/FCM" ([Happy README](https://github.com/slopus/happy)). ntfy's iOS app works the same way. A self-hosted ntfy server must forward to `ntfy.sh` to get instant iOS pushes, because iOS "makes it impossible to implement instant push notifications without a central server." The forwarded request carries only a message ID ([ntfy docs: config](https://docs.ntfy.sh/config/)). For TBD this would be exactly the maintainer-hosted backend it has ruled out. The other choice is for each user to build the app under their own $99 account.
- **What native buys** – Notification buttons that work from the lock screen: "Tapping a button sends the selected action to the app, which then processes the action in the background" ([Apple: Declaring your actionable notification types](https://developer.apple.com/documentation/usernotifications/declaring-your-actionable-notification-types)). A notification service extension can "decrypt data sent in an encrypted format" before display ([Apple: Modifying content in newly delivered notifications](https://developer.apple.com/documentation/usernotifications/modifying-content-in-newly-delivered-notifications)). The app can also keep keys in the Keychain or Secure Enclave. It still gets no background socket. Apple treats background pushes as low priority and says "don't try to send more than two or three per hour" ([Apple: Pushing background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)).
- **Who would own it** – Someone must hold the developer account, answer App Review, renew every year, keep up with each new iOS SDK, publish a privacy policy, and run the push gateway. TBD is written in Swift, so a SwiftUI client could share Codable models with the Mac code. That sharing is unverified, since the shared module may use macOS-only APIs. For a multi-tenant open-source project, this is a standing operational commitment by one person.

## 3. Reusing an app the user already has

All of these remove the client build and give push for free. All of them let the platform read every message, which ends the end-to-end goal for anything sent through them.

- **Telegram** – The best fit of the chat apps.
  - **Transport** – A bot can receive updates by long polling with `getUpdates` instead of a webhook ([Telegram Bot API](https://core.telegram.org/bots/api)). The laptop can poll from behind NAT with no relay at all.
  - **Prompts** – Inline keyboard buttons send a callback of "1-64 bytes" back to the bot (same page). That is enough for a choice ID or approve and deny.
  - **Rendering** – Messages are "1-4096 characters." The markup supports `pre` and `code` blocks and collapsed "expandable_blockquote" sections (same page). Long transcripts must be split into chunks or summarized.
  - **Privacy** – Bot chats are cloud chats, which use "server-client encryption." Telegram describes end-to-end encryption only for secret chats ([Telegram FAQ](https://telegram.org/faq)). Its bot docs describe no way for a bot to use a secret chat (unverified as an absolute).
  - **Hybrid option** – A bot can open a Mini App, a web page loaded inside Telegram from the developer's URL ([Telegram Mini Apps](https://core.telegram.org/bots/webapps)). The bot could send a terse notification with a button. The button could open the same static client, which talks to the relay with end-to-end encryption. Mini Apps get `SecureStorage`, which "on iOS … uses the system Keychain," limited to 10 items (same page). Telegram's servers would see only the notification text. The Telegram app itself, which hosts the web view, joins the trust base.
  - **Setup** – Each user creates a bot and gives TBD its token.
- **Slack**:
  - **Transport** – Socket Mode delivers events and interactive payloads over a WebSocket "instead of sending payloads to a public endpoint," which works behind a firewall ([Slack: Using Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)). Block Kit buttons arrive the same way.
  - **Limits** – "Apps using Socket Mode are not currently allowed in the public Slack Marketplace" (same page). Each user would create their own Slack app. The free plan shows 90 days of history, deletes content after a year, and allows 10 integrations ([Slack: Free plan changes](https://slack.com/help/articles/7050776459923-Pricing-changes-for-the-Pro-plan-and-updates-to-the-Free-plan)).
  - **Privacy** – Slack and workspace admins can read everything. Posting code and agent transcripts into an employer's workspace raises data-governance questions that TBD should not create by default.
- **Discord**:
  - **Transport** – A bot receives button and select-menu interactions over its gateway connection or a webhook ([Discord: Receiving and responding to interactions](https://docs.discord.com/developers/interactions/receiving-and-responding)). The gateway is outbound, so it works behind NAT.
  - **Privacy** – Discord's end-to-end encryption covers audio and video only. Text messages "are not end-to-end encrypted" ([Discord: Meet DAVE](https://discord.com/blog/meet-dave-e2ee-for-audio-video)).
- **iMessage** – There is no bot API for individuals. Apple Messages for Business requires an Apple-approved messaging service provider, and "only official brand owners qualify" ([Apple Messages for Business documentation](https://register.apple.com/resources/messages/messaging-documentation/)). Not viable.
- **Apple Shortcuts** – The "Get Contents of URL" action can send GET, POST, PUT, PATCH and DELETE requests with a JSON body and read JSON back ([Apple: Request your first API in Shortcuts](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios)). Shortcuts can show results and menus. But a shortcut cannot receive a push or hold a connection, and the action list has no encryption step (unverified as an absolute). It can only talk to a plaintext API. At most it could be a "send a message to session X" helper, which conflicts with an end-to-end design. It cannot be the client.
- **ntfy (not asked, but relevant)** – An open-source push app with notification action buttons. It only notifies, and its iOS path depends on `ntfy.sh` as described in section 2. End-to-end encryption is not described in its config docs (unverified).
- **Claude Code Remote Control (not a reusable app, but overlapping)** – Users with a Claude subscription can already drive a Claude Code session from the Claude app ([Claude Code docs: Remote Control](https://code.claude.com/docs/en/remote-control)). It covers neither Codex sessions nor TBD's session list. It stores transcripts on Anthropic's servers, and some organization policies turn it off. Its pairing UX is a useful reference. The terminal shows a QR code that opens the session on the phone.

## 4. Rendering

**What a transcript view on a phone needs:**

- **Session list** – Name, worktree, agent (Claude or Codex), state (working, waiting for input, waiting for approval, idle), and last activity. Sessions that need the user sort to the top.
- **Markdown** – Headings, lists, links (opened outside the app), inline code, and tables that scroll sideways instead of squeezing.
- **Code blocks** – Monospace, horizontal scroll, a wrap toggle and a copy button. Syntax highlighting is optional.
- **Tool calls collapsed** – One line per call, such as "Edit `src/app.ts`" or "Bash `npm test`", that expands with `<details>`. Large tool output stays collapsed or truncated and is fetched on demand.
- **Diffs** – Edit tool inputs carry old and new text. Show them as a unified diff with red and green lines. A file write shows the path and line count.
- **Thinking blocks** hidden by default.
- **Prompts** – Multiple-choice questions as large buttons. Permission requests show the exact command or diff being approved, with Allow and Deny.
- **Composer** – A text box, send, and an interrupt button.
- **Long transcripts** – Render the latest page and load older entries on scroll. `content-visibility: auto` reached Safari only in version 26 ([MDN compat data](https://github.com/mdn/browser-compat-data/blob/main/css/properties/content-visibility.json)), so do not depend on it.

**Security of rendering.** Transcript content is untrusted. It contains tool output, file contents and fetched web pages. Script injection into this page would expose the keys. "Marked does not sanitize the output HTML," and its docs recommend DOMPurify ([marked](https://marked.js.org/)). Turn raw HTML off in the markdown parser, run the output through DOMPurify, and keep the strict CSP from 1.7. The laptop should send a compact, normalized event model rather than raw JSONL lines. That keeps payloads small and keeps the parsing that matters on the trusted side.

**Size.** Sizes below were measured on 2026-11-07. Each library was downloaded from jsDelivr at the current npm version and compressed with `gzip -9`. The marked and jsQR files are unminified builds, so they overstate a minified bundle.

| Library (version) | Role | Gzipped KB |
|---|---|---|
| preact (11.2.0) | UI library, optional | 4.8 |
| preact hooks | optional | 1.6 |
| lit-core (3.x) | UI library, optional | 6.1 |
| marked (18.1.3) | markdown | 15.4 |
| DOMPurify (3.4.17) | sanitizer | 11.7 |
| Prism core (1.30.0) | highlighting, optional | 3.2 |
| highlight.js common bundle (11.12.0) | highlighting, alternative | 43.5 |
| jsdiff (9.0.0) | diffs | 9.9 |
| jsQR (1.4.0) | QR decoding, pairing screen only | 56.8 |

A client with no framework would load about 40 KB of libraries (marked, DOMPurify, Prism core, jsdiff) plus its own code, likely 15 to 30 KB (unverified estimate). Preact or Lit adds about 5 to 6 KB. Either way the app is small next to any phone's budget. The choice is about readability for auditors. Plain ES modules served as written, with no build step, are the easiest for a user to check against the repo. Preact without JSX, or Lit, keeps that property.

## Recommendation for TBD

1. **Build a PWA, not a native app, for the first version.** It needs no developer account, no App Review, and no push gateway, and it works on iOS and Android from one codebase. The one real loss is lock-screen Allow and Deny on iOS. Revisit a native app only if that becomes the main complaint, and only if someone takes ownership of the developer account, App Review and a push gateway. A gateway would break the no-hosted-backend rule, so that would be a policy change, not just an engineering task.
2. **Serve the client from a static origin built from the public repo, never from the relay.** Give it a dedicated origin before the first release, because the origin cannot change later without every user pairing again. A GitHub organization used only for this, or a custom domain on GitHub Pages, both work. `cheapsteak.github.io/tbd/` works only if every other Pages site on that account is held to the same standard, since they share storage with the client. Let users point TBD at their own fork's URL.
3. **Make the laptop the Web Push sender.** It holds the VAPID key and the phone's subscription and posts RFC 8291-encrypted pushes directly to Apple or Google. The relay carries only end-to-end-encrypted session traffic and never touches notifications. Keep notification text short and let users hide session names.
4. **Target iOS 17 and later.** Use the Declarative Web Push payload format on iOS 18.4 and later. Keep a service worker that handles the same payload on Android and older iOS. Whether Chrome reads the declarative format natively is unverified, so the worker must not assume it.
5. **Use P-256 ECDH, HKDF and AES-GCM for stored keys.** Generate them non-extractable, store them in IndexedDB, and call `navigator.storage.persist()`. Do not store X25519 keys until WebKit bug 312279 is fixed. Test every stored key type on a real iPhone.
6. **Pair inside the installed app.** Show an install QR first, then a pairing QR that the app scans with its own camera view, with a short typed code as the fallback. Do not rely on the Camera app handing a `#fragment` secret to the installed app.
7. **Treat the socket as foreground-only.** Reconnect on `visibilitychange` and resume from the last event cursor. Make every message idempotent. A notification tap should open the waiting session directly.
8. **Keep the client small and auditable.** Plain ES modules or Preact, with marked, DOMPurify, jsdiff and Prism vendored into the repo. Raw HTML stays off, a strict `<meta>` CSP is set, and jsQR loads only on the pairing screen. Require review on changes to the client directory, because merging is the deploy.
9. **Leave chat-app integrations out of version 1.** If users ask for them later, a Telegram bot that sends only "session X needs you" alerts is the lowest-cost add-on. Its Mini App could open the same encrypted client, so transcripts would never pass through Telegram's servers.

**Check on a device before building on these:**

- Stored P-256 and Ed25519 keys survive an IndexedDB round trip in a Home Screen app.
- What "Add to Home Screen" does with the current URL and fragment on iOS 26.
- How quickly iOS kills a backgrounded socket.
- Whether Chrome on Android shows a Declarative Web Push payload without a service worker.
