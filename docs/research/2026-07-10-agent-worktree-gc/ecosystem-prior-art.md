# Prior art: GC of git worktrees created by/for AI coding agents (web research report)

*Researched 2026-07-10 (web search + primary-source fetches), as prior art for TBD's disk-reclaim / agent-worktree GC work (PR #423, issue #420). Companion report: [`agent-deck-worktree-lifecycle.md`](agent-deck-worktree-lifecycle.md).*

Context: Claude Code's `isolation: worktree` subagents and Workflow runs create git worktrees under `<repo-root>/.claude/worktrees/agent-*` and `wf_*`. Claude Code auto-removes one only if it ended UNCHANGED; once an agent commits, the worktree persists (by design, so the branch survives). They accumulate massive disk (e.g. 81 worktrees, dominated by per-worktree `node_modules`/`.venv`, in one incident).

## Angle 1 — Claude Code itself

**Claude Code now HAS a built-in GC sweep for agent worktrees — and it structurally misses the committed-but-unpushed case.** Per the official worktrees doc (https://code.claude.com/docs/en/worktrees.md, "Clean up worktrees"):

- **Session-end path** (`--worktree` / EnterWorktree): clean worktree (no uncommitted changes, no untracked files, no new commits) → auto-removed with its branch; dirty or committed → interactive keep/remove prompt; `-p` non-interactive runs are never cleaned.
- **Startup sweep for subagent + background-session worktrees**: removed automatically once older than the `cleanupPeriodDays` setting, *provided they have no uncommitted changes, no untracked files, and **no unpushed commits***. `cleanupPeriodDays` defaults to 30 (https://code.claude.com/docs/en/settings.md), the same knob that GCs transcripts/tasks/shell-snapshots. User `--worktree` worktrees are exempt from the sweep.
- **Why worktrees still accumulate forever in practice**: the sweep's "no unpushed commits" condition means exactly the incident case — an agent that committed but never pushed — is permanently exempt. Committed-but-unmerged `agent-*` worktrees never age out even with the sweep. Plus 30 days is a long window for a fast-moving multi-agent repo.
- **Locking**: while an agent runs, Claude runs `git worktree lock` on its worktree so a concurrent sweep can't remove it; unlocked on finish (changelog v2.1.157: "Worktrees managed by Claude are now left unlocked when the agent finishes, so `git worktree remove`/`prune` can clean them up"). v2.1.196 fixed background agent worktrees under `.claude/worktrees/` being orphaned after the 30-day job retention sweep; v2.1.187 fixed leaked locked `.git/worktrees/` registrations from killed agents.
- **Location config**: default `<repo>/.claude/worktrees/<name>`, branch `worktree-<name>`; relocatable only via a `WorktreeCreate` hook (which replaces git logic entirely, and disables `.worktreeinclude` processing). `WorktreeRemove` hook exists for custom cleanup. `worktree.baseRef` (`fresh`|`head`) controls base.
- **Disk mitigation settings**: `worktree.symlinkDirectories` (symlink `node_modules` etc. from main checkout into worktrees) and `worktree.sparsePaths` exist — but issue #40259 documents that symlinkDirectories **breaks the auto-cleanup**: `git worktree remove` refuses because the symlinks count as untracked files, so cleanup silently fails (https://github.com/anthropics/claude-code/issues/40259).
- **Community pain, closed as not-planned/duplicate**:
  - #55435 — 48 dirs / 11 GB in 9 days from `isolation:"worktree"` planning waves; proposed terminal-state reap + `claude doctor`-style bulk prune of worktrees whose owning PID is dead; **closed not-planned** (https://github.com/anthropics/claude-code/issues/55435).
  - #57767 — proposes "N leftover worktrees" session-start notice, `/cleanup-worktrees` command, `WorktreeRemove` hook `retry|force|skip` decisions, opt-in `autoCleanupOnChanges` that stashes/patches diffs before force-remove; closed duplicate (https://github.com/anthropics/claude-code/issues/57767).
  - #26725 — stale worktrees never cleaned, orphaned branches undeletable because checked out; still open (https://github.com/anthropics/claude-code/issues/26725).
  - #41010 — a cleanup bug that deleted the *parent's* working dir on an agent-ID prefix collision — a cautionary tale for path-pattern-matching reapers.
  - #60113 — asks for reusing heavy dependency dirs across agent worktrees.
- **No provenance**: nothing links `.claude/worktrees/agent-*` to the spawning session; #55435's dead-PID check and #57767's visibility notice are the only proposed provenance-ish mechanisms, both rejected.

## Angle 2 — How other agent-worktree tools clean up

Every serious tool in this space converged on one of four patterns (often combined):

**(a) LRU/count-cap reaper (Codex app, Cursor)** — the strongest prior art:
- **OpenAI Codex app** (https://learn.chatgpt.com/docs/environments/git-worktrees): worktrees live *outside the repo* in `$CODEX_HOME/worktrees` (configurable root). Two tiers: "Codex-managed" (per-task, reapable) vs "permanent" (user-created, never auto-deleted). Auto-deletes when the task is archived or when the count exceeds a limit — "By default, Codex keeps your most recent 15 Codex-managed worktrees." Exemptions: pinned conversations, in-progress tasks, permanent worktrees. Crucially: **"Before deleting a managed worktree, Codex saves a snapshot of the work on it"** and offers restore if you reopen the task — this is how they reap dirty/committed worktrees safely. Known bug: local-environment *cleanup scripts* don't run on archive-triggered reaps (openai/codex#19480).
- **Cursor** (https://cursor.com/docs/configuration/worktrees): machine-wide worktree root (outside repos), setup via `.cursor/worktrees.json` scripts, and automatic cleanup via `cursor.worktreeCleanupIntervalHours` (default 6h sweep) + `cursor.worktreeMaxCount` (default 25 per machine, oldest evicted), plus manual `/delete-worktree`. Cursor explicitly recommends **against symlinking dependencies**; "use fast package managers (bun/pnpm/uv) for fresh installs." Forum threads document 9.8 GB in 20 minutes on Windows before users found the knobs (https://forum.cursor.com/t/windows-request-to-disable-automatic-worktree-creation-critical-disk-space-issue/146189).

**(b) State-machine/TTL GC tied to task status (vibe-kanban)**: a background garbage-collector service removes worktrees whose task is in `Done` or `archived` state after ~1 hour; deleting a task removes worktrees immediately; branch deletion is separate and still pending (PR #1661). Maintainer confirmation: https://github.com/BloopAI/vibe-kanban/discussions/2335; configurable-retention request: https://github.com/BloopAI/vibe-kanban/issues/765; merge-didn't-clean-up bug: issue #1764. This is the closest analog to TBD (DB-backed task↔worktree provenance driving GC).

**(c) Merge-triggered teardown (claude-squad, agent-deck, workmux, uzi)**: cleanup is part of the "finish" verb, not a background process. claude-squad (https://github.com/smtg-ai/claude-squad) creates a worktree per agent and removes it when you merge/finish. agent-deck (https://github.com/asheshgoplani/agent-deck) has `worktree finish "<session>"` (merge branch → remove worktree → delete session) plus `worktree cleanup` for orphans, a pre-removal `.agent-deck/worktree-destruction.sh` hook (runs while the worktree still exists, for stopping containers etc.; failure warns but removal proceeds), and a 30-second undo window on session delete. uzi has `uzi kill all` (tears down tmux sessions + worktrees).

**(d) Archive-as-delete with restore (Conductor, Crystal, Codex)**: Conductor (https://www.conductor.build/docs/workflow) archives finished workspaces — archiving deletes the workspace directory but preserves chat history and supports restore from the History pane; an `archive` script hook cleans external resources. Crystal/Nimbalyst removes worktrees when sessions are deleted and offers archiving as the softer alternative. Claude Code *Desktop* also archives sessions, and had a real bug where manual Archive force-removed a worktree with uncommitted changes, no confirmation (anthropics/claude-code#56639) — evidence that "archive must check dirty state or snapshot first" is a learned lesson across the ecosystem.

**Sculptor (Imbue)** sidesteps worktrees entirely — per-agent Docker containers with background "cleanup scripts... to garbage collect unused sculptor docker volumes" (https://imbue.com/sculptor/, https://docs.imbue.com/changelog). Interesting mainly as confirmation that everyone needs a volume/checkout GC of some kind.

**gwq** (https://github.com/d-kuro/gwq), an AI-agent-oriented worktree CLI: `gwq remove` with dry-run, pattern matching, `-b` to also delete the branch, `--force-delete-branch` for unmerged branches; `gwq prune` wraps metadata cleanup. No TTL reaper — manual with good safety UX.

## Angle 3 — git semantics + merged-branch detection

From https://git-scm.com/docs/git-worktree:
- `git worktree remove` refuses unclean worktrees (untracked files or modified tracked files) without `--force`; locked worktrees need `--force --force`. **It never deletes the branch** — branch GC is always a separate step, and `git branch -d/-D` refuses while the branch is checked out in any worktree (the exact trap in claude-code#26725: remove worktree first, then delete branch).
- `git worktree prune` deletes only administrative metadata in `$GIT_DIR/worktrees` for working trees whose directories are missing — it never deletes directories. So the fast-reap recipe used in the wild for huge trees is `rm -rf <dir>` + `git worktree prune` (the sequential unlink walk of `git worktree remove` is slow on 10k+ files; noted e.g. in https://zylos.ai/research/2026-02-22-git-worktree-parallel-ai-development/).
- `git worktree lock --reason` is the sanctioned "do not reap" marker; Claude Code itself uses lock-while-running as its concurrency guard. A TBD reaper should honor locks and could use `lock --reason` as its own keep-pin.
- **Squash-merge detection** (needed because `git branch --merged` returns nothing for squash-merged branches): the established pattern is the `git-delete-squashed` technique — find `merge-base main branch`, build a synthetic squash commit with `git commit-tree <tree-of-branch-tip>`, then `git cherry main <synthetic>`; a `-` prefix means an equivalent patch already landed. Sources: https://github.com/not-an-aardvark/git-delete-squashed, https://adamj.eu/tech/2022/10/30/git-how-to-clean-up-squash-merged-branches/, worktree-aware alias set at https://gist.github.com/nikitagor-zen/1880733cab88467c5ac14dbbd8b10973 (explicitly skips branches checked out in worktrees). Where a PR exists, `gh pr view --json state,mergedAt` / branch-gone-on-remote (`[gone]` after `fetch --prune`) is the more robust signal — TBD already has a `clean_gone`-style flow for that.

## Angle 4 — Making per-worktree installs cheap instead of reaping them

- **pnpm has a dedicated official page for exactly this scenario**: "pnpm + Git Worktrees for Multi-Agent Development" (https://pnpm.io/next/git-worktrees) — `enableGlobalVirtualStore: true` makes each worktree's `node_modules` just symlinks into one content-addressable store; subsequent worktree installs are "nearly instant" and near-zero marginal disk. Even they conclude with: remove unused worktrees with `git worktree remove`, "leftover worktrees are cheap but can accumulate."
- **uv**: `link-mode` defaults to `clone` (Copy-on-Write / APFS clonefile) on macOS (https://docs.astral.sh/uv/reference/settings/#link-mode), so per-worktree `.venv`s already share blocks with the global cache on APFS — `du` overstates their true cost (`nlink=1` on a clone; only a delete-and-`df`-delta measures real reclaim). Same applies to pnpm `link-mode: clone`/`clone-or-copy`.
- Symlinking `node_modules` across worktrees is the tempting-but-wrong shortcut: Cursor explicitly recommends against it; Claude Code ships it (`worktree.symlinkDirectories`) and it broke their own cleanup (#40259) and file-write semantics (#40857). Per-branch dependency drift is the other failure mode.
- Nothing surveyed dedupes `.build`-style compiled artifacts across worktrees; SwiftPM `.build` is non-relocatable, so reaping/`.build`-scoped GC remains the right tool there.

## Patterns observed in the wild (summary)

| Pattern | Who | Notes |
|---|---|---|
| Age/TTL sweep, clean-only | Claude Code CLI (`cleanupPeriodDays`, 30d) | Skips dirty/untracked/**unpushed** → committed agent worktrees never reaped |
| Count-cap LRU + snapshot-before-delete | Codex (15), Cursor (25, 6h interval) | Snapshot/restore makes reaping dirty trees safe; pinned/in-progress/permanent exempt |
| Task-state GC with short TTL | vibe-kanban (Done/archived + 1h) | Requires provenance (task↔worktree DB) |
| Merge/finish-triggered teardown | claude-squad, agent-deck, uzi, vibe-kanban merge flow | Cleanup as part of the "ship" verb; pre-removal hook script |
| Archive-as-delete + restore | Conductor, Crystal, Codex, CC Desktop | Directory deleted, metadata/chat kept, restorable |
| Provenance markers | agent-deck sessions, vibe-kanban tasks, CC (none — dead-PID check proposed and rejected in #55435) | |

## Recommendations for TBD's reaper

1. **Adopt the Codex hybrid: count-cap LRU + snapshot-before-delete.** A pure TTL misses burst accumulation (81 worktrees in days); a count cap (Codex 15, Cursor 25) bounds worst-case disk regardless of rate. Before reaping anything with unmerged/uncommitted work, snapshot it (`git bundle create` of the branch + `git stash create`/patch of the dirty state, stored compactly) so the reap is reversible — this is the single pattern that lets every tool reap *committed* worktrees, which is exactly the case Claude Code's own sweep refuses to touch.
2. **Layer the safety checks the ecosystem converged on**, in order: skip locked worktrees (`git worktree lock` is the cross-tool "in use" signal — Claude Code sets it while agents run); skip worktrees with a live attached process/session (TBD's DB knows this, unlike everyone else); treat dirty (`--force`-requiring) as snapshot-then-remove or keep, never silent force-remove (the #56639 / #41010 failure class).
3. **Reap in three explicit tiers**: (a) branch merged into main (regular merge via `--merged`, squash via the synthetic-squash `git cherry` check or `gh pr` state / `[gone]` remote) → remove worktree + delete branch, no snapshot needed; (b) unmerged but idle past TTL/LRU → snapshot then remove worktree, *keep the branch* (the branch is cheap; the checkout + node_modules is the disk); (c) never touch user-pinned or session-named worktrees — mirror Claude Code's exemption of `--worktree` and Codex's "permanent" tier.
4. **Delete branch and worktree as one transaction only in tier (a)**, and always worktree-first (branch deletion fails while checked out — claude-code#26725).
5. **For `.claude/worktrees/agent-*`/`wf_*` specifically**: these are inside repos TBD manages but not TBD-created. Prior art says surface-then-offer, not silent reap (issue #57767's "N leftover worktrees" notice was the community's ask). Claude Code's own sweep will handle the clean ones after 30 days; TBD's added value is the committed-but-unpushed ones the sweep exempts — tier (b) with snapshot applies. Beware exact-prefix matching bugs (#41010).
6. **Use fast-remove for big trees**: `rm -rf` + `git worktree prune` rather than `git worktree remove` on multi-GB checkouts; `prune` only clears `$GIT_DIR/worktrees` metadata so this is safe once the dir is gone.
7. **Disk-cost reduction is complementary, not a substitute**: recommend/pre-configure pnpm `enableGlobalVirtualStore` and rely on uv's default APFS clone mode; don't symlink `node_modules` across worktrees (breaks removal + branch drift). SwiftPM `.build` stays a reap target (non-relocatable).
8. **Provenance**: TBD's DB already gives worktree↔session linkage nobody else has for Claude's agent worktrees; recording "spawned-by session / last-attached time" per worktree is what turns TTL from guesswork into "idle since last session detach" — the vibe-kanban model.
