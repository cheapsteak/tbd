# Hang-stack reclaimer: a named reconciler for `~/Library/Logs/TBD/hang-stacks/`

## Problem

`HangStackWriter` (`Sources/TBDApp/Diagnostics/HangStackWriter.swift`) writes
one file per main-thread hang event into `~/Library/Logs/TBD/hang-stacks/`,
appending resamples while the stall lasts. It has no prune, no cap, and no
retention policy. The directory therefore grows for the lifetime of the
install: on the machine this design was written against it held **25,799 files,
~300 MB**, accumulated since the writer was introduced.

This is a textbook instance of the shape
[`docs/specs/2026-08-15-named-reconciler-doctrine-design.md`](2026-08-15-named-reconciler-doctrine-design.md)
describes. Hang-stack files are a durable external resource — bytes on disk that
outlive the request that created them — and no sweep covers them. Every
unbounded leak found in the wild so far has had exactly that property, and every
resource a reconciler does cover has stayed healthy. The fix is not better
create-time hygiene; it is naming an owner.

## What the resource is

A hang-stack file is a throwaway diagnostic sample: a header (timestamp, pid,
stall duration, focused terminal, pane, transcript item count) and one or more
formatted main-thread backtraces. It is machine-generated, never user-authored,
holds no credentials and no user content, and is regenerated by the next hang.
Its value decays fast — a stack is read while investigating the hang that
produced it, or during the days-long soak of a performance change, and is dead
weight after that. 25,799 of them is far past any plausible use.

That characterisation is what drives every decision below, so it is worth
stating plainly: unlike a profile config directory, an orphaned hang stack is
not the only copy of anything.

## Decisions

### Who reclaims: `OrphanGC`, daemon-side

The reclaimer is a new collector, `HangStackCollector`, run as an additional
phase of `OrphanGC.sweep()` — the hourly daemon sweep — rather than an app-side
prune next to the writer.

The tension is real and worth stating: the writer is app-side, and the directory
is under `~/Library/Logs`, not `~/tbd`. Neither fact points away from the daemon
once examined.

- **The daemon can reach it.** It runs as the same user with the same home, and
  reclaiming needs no app state — only the directory, its file names, and their
  modification times. `~/Library/Logs/TBD/hang-stacks` is simply the first GC
  target outside `~/tbd` and `/private/tmp`; the sweep's scope is "durable
  resources TBD creates", never one tree.
- **The app is the process that hangs.** A reclaimer living inside TBDApp
  competes with the very stalls it exists to bound, and stops running exactly
  when the app crashes or is killed — the runs that leave the most files behind.
  The daemon outlives app restarts.
- **The sweep already exists, with everything a reclaimer needs.** Hourly
  cadence, the `gcEnabled` master switch, `dryRun` planning through
  `tbd gc sweep --dry-run`, per-phase soak flags, and a keep-biased failure
  discipline. An app-side prune would be a second, weaker instance of that
  mechanism: a new timer, a new flag surface, no dry run, no master switch. The
  doctrine's whole argument is that consolidating on named sweeps beats
  scattering ad-hoc cleanup.

The write side stays in the app, because only the app writes (below).

### Retention: 14 days, and never more than 1000 files

A candidate is deleted when it is **older than 14 days** *or* **outside the
newest 1000 files** by modification time. Both, not either alone:

- **Age is the policy that matches how the artifacts are used.** You read a hang
  stack from the hang you just had, or from this week's soak. Fourteen days
  spans a soak plus the weekend on either side, which is the longest window
  anyone has plausibly needed to reach back through.
- **The count cap is the bound age cannot give.** The failure that produced
  25,799 files is a hang *storm* — a chronic stall loop writing files far faster
  than they age out. Age alone leaves that unbounded inside its own window,
  which is precisely how the directory got here. At the observed ~11.6 KB per
  file, 1000 files is roughly 12 MB: a ceiling low enough to be irrelevant and
  high enough that no realistic investigation loses a sample it wanted.

A **grace period** sits in front of both: files modified within
`gcGraceSeconds` (default 1 h) are kept regardless. This reuses the knob the
other collectors already gate on, and here it does one specific job — the app
may hold the newest file open, appending resamples. Unlinking an open file is
safe on POSIX (the app keeps writing to the unlinked inode), but silently
discarding the stack of a hang in progress is a bad trade for nothing, and the
grace makes it unreachable. Neither policy would select the newest file anyway;
the grace makes that a guarantee rather than an accident.

Total-bytes is deliberately *not* a third policy. File size is bounded in
practice by the writer's own resample cadence, the count cap already bounds the
directory to ~12 MB, and a third knob buys a bound the first two already give
while adding a `stat` of every file and a third thing to explain.

### Delete outright, not quarantine

The profile-dir collector quarantines because an orphaned profile directory
holds credentials and user content with no other copy, and a misclassification
there is unrecoverable. Neither half of that applies here.

Hang stacks are machine-generated diagnostics; a misclassified one costs a
backtrace nobody was reading, and the next hang writes another. More to the
point, quarantining would **relocate the leak rather than end it**: a
`.reaped/` directory of hang stacks is itself an unbounded directory of hang
stacks, needing its own expiry pass to bound — extra mechanism whose only
purpose is to defer a delete that carries no risk. Copying the profile-dir
pattern here would be cargo cult.

### No `ReapRecord` per file

Every other collector persists one `ReapRecord` per reap, and this one
deliberately persists none.

`ReapRecord` exists to make a reap listable and (for agent worktrees)
restorable. A hang stack is not restorable, belongs to no repo, and so would
never surface in the app's per-repo Reclaimed section. And the numbers make it
actively harmful: one row per file means the first sweep of a directory like
today's writes ~25,000 rows into `reap_records` — creating a new unbounded
table to record the end of an unbounded directory. A reclaimer that leaks is
not a reclaimer.

Instead the phase reports in aggregate: one plan line —
`REAP hang-stacks <dir> files=<n> bytes=<n>` — and one `.info` log line per
sweep that reclaimed anything. The plan line is aggregated for the same reason
the records are: 25,000 lines in an RPC response is not a plan anyone reads.

A dry run emits that same `REAP` line whether or not the flag is on, matching
the profile-dir phase. The line answers "what would this reclaim", which is
exactly the question someone deciding whether to enable a default-off flag is
asking; reporting the selection as a `KEEP` because the flag happens to be off
would answer a question nobody asked and hide the one number that matters.

The files reclaimed are counted into `GCSweepResult.reaped` so
`tbd gc sweep` reports honestly, but they do **not** trigger the
`.reapRecordsChanged` broadcast, which stays keyed to phases that actually
insert records.

### A write-side cap as well as the sweep

The doctrine treats create-time cleanup as best-effort and the sweep as the
guarantee. It does not say skip the cheap create-time bound, and here that bound
covers a gap the hourly sweep genuinely leaves: a hang storm can write hundreds
of files between two sweeps.

So `HangStackWriter.recordHangStart` trims the directory to the newest
`HangStackRetention.maxFiles` after writing its new file. Count only — the age
half is the sweep's job, and the writer should do one cheap thing. It runs on
the watchdog's background utility queue, never the main thread, and in steady
state enumerates a directory the sweep has already bounded to ~1000 entries.

Writer and collector read the same constants from
`HangStackRetention` in `TBDShared`, so the two bounds cannot drift apart.

### One flag, daemon-side, covering both halves

Deleting persisted state from a background sweep trips the house default-off
rule, so the phase ships behind `gc_hang_stacks_enabled`: a new `config` column,
added by a `.sql` migration with **no SQL default**, so NULL stays the third
state and the shipped default lives in exactly one place —
`?? Config.gcHangStacksEnabledDefault` (= `false`) in `ConfigRecord.toModel()`.
Read on top of `gcEnabled`, like the other per-phase gates. `dryRun` plans
regardless of the flag, exactly as the other phases do: deciding whether to
enable a default-off flag requires seeing what enabling it would reclaim.

The write-side cap answers to the **same** flag rather than a second app-side
`UserDefaults` twin. Two flags for one behavior is sprawl, and worse, it makes
"is the reclaimer on?" a question with two answers. The app already loads
`Config` at launch and on config-change deltas; it mirrors the resolved value
into `HangStackWriter`. The mirror starts OFF and stays OFF whenever the daemon
is unreachable — the keep-biased direction, and the same answer an unset column
gives.

Enablement for the soak is `tbd gc hang-stacks on`, mirroring
`tbd gc profile-dirs` and `tbd gc orphan-processes`. No app UI toggle before
graduation.

## Mechanics

`HangStackCollector` (`Sources/TBDDaemon/GC/HangStackCollector.swift`) owns
filesystem enumeration and deletion and holds no database access, matching
`ScratchpadCollector`. `OrphanGC` owns the gating and the reporting.

**Candidates.** Immediate children of the base directory that are regular files
whose name matches the writer's own shape — `hang-` prefix, `.txt` suffix. A
whitelist, not a blacklist: the directory is not TBD's to empty, and anything
the writer did not produce (a user's notes, a copied sample, a subdirectory) is
never a candidate. Entries whose resource values cannot be read are kept —
absence of evidence, not evidence of absence.

**Ordering and selection.** Candidates are sorted newest-first by
`contentModificationDate` (falling back to `creationDate`, and keeping the file
when neither is readable). A file is selected for deletion when its age exceeds
`maxAge`, or its index in that order is `>= maxFiles`. Files younger than
`gcGraceSeconds` are removed from consideration before either test.

**Deletion.** Sizes are summed from the already-fetched
`fileSizeKey` — no `du` subprocess, since these are single small files. Each
delete is guarded by the same anchor check `ScratchpadCollector` uses: the path
must resolve strictly under the base. A failed `removeItem` logs and moves on;
the next sweep retries.

**Absent directory.** No-op. A machine where the app has never hung has no
directory, and creating one to sweep it would be absurd.

**Injection.** `OrphanGC` takes `hangStackBase: URL? = nil` alongside
`scratchpadBase` and `profileDirBase`, so tests never point the collector at the
developer's real `~/Library/Logs`. The production default derives from the
user's home, which `scripts/test.sh` also fences via `HOME`/`CFFIXED_USER_HOME`
— belt and braces, since the fence and the injection each suffice alone.

No new timer and no new delay: the phase runs inside the existing sweep, and
compares persisted timestamps rather than measuring elapsed behaviour. Per the
house rule that is the date seam's business, and `OrphanGC` already carries the
injected `now`.

## Tests

- **Flag off, nothing is reclaimed** — a directory of 2,000 old files survives a
  non-dry sweep untouched; flag on, it is trimmed to the newest 1000 with
  everything past 14 days gone.
- **Both branches of the write-side cap** — the writer leaves the directory
  alone when its mirrored flag is off, and trims to `maxFiles` when on.
- **Three flag states are distinguishable** — a pre-migration row reads NULL
  rather than `0`; an explicit `false` survives a change to the default
  constant; NULL follows it. (The `ConfigStore.toModel` default-parameter seam
  the sibling flags already use.)
- **Grace protects the newest file**, including one still open for appending.
- **Whitelist holds** — a non-matching file and a subdirectory in the base
  survive a sweep that deletes everything else.
- **Unreadable dates keep**, never delete.
- **Aggregation** — a sweep that reclaims 2,000 files adds one plan line and
  zero `reap_records` rows.

## Graduation

Soak with `tbd gc hang-stacks on` on the development fleet. Graduation is a
one-line change to `Config.gcHangStacksEnabledDefault`, which reaches every
install that never touched the toggle and preserves every explicit opt-out.
Delete the flag once the default has been on through a release.

The pre-existing 25,799 files are cleaned up separately, by hand. This design
deliberately does not special-case the backlog: the first sweep after the flag
is enabled reclaims it through the ordinary path, which is the honest test of
whether the ordinary path works.
