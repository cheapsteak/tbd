# Design: Reclaim worktree SwiftPM `.build` disk

*2026-07-08. Grounded in `~/projects/longeye-docs/disk-cleanup/tbd-swiftpm-build-lessons.md`
(the disk-full incident investigation), live measurement on this machine, and a
web-research pass on SwiftPM/worktree prior art.*

## Problem

Every TBD worktree that builds the tbd Swift package produces a SwiftPM `.build/`
directory of **~5.5 GiB**, with **zero sharing** across worktrees (fully real,
`du`-honest bytes). Worktrees routinely outlive their sessions, so `.build` dirs
accumulate until hand-deleted. On this 460 GB machine that pool has hit 55 GiB
across 14 worktrees and driven the disk to near-0 free three times in ~5 weeks,
killing unrelated processes mid-write.

Cleanup today is manual (`du` + `rm`) and loses to normal usage within days.

**Goal:** keep the steady-state `.build` footprint low automatically, so the
developer never runs `du`/`rm` by hand. Crash prevention is a welcome side
effect, not the design target — steady-state reclamation is.

## Measured composition (identical across all live worktrees, 2026-07-08)

| Chunk | Size | % | What it is | Reclaim safety |
|---|---|---|---|---|
| `index-build/` | 2.6 GiB | 47% | SourceKit-LSP's **separate** background-index build | Disposable — nothing runtime reads it; regenerates on demand |
| `arm64-apple-macosx/` | 2.0 GiB | 37% | The real debug build (`debug/` symlinks into it; the running/testable app lives here) | Needed while active; one cold rebuild if deleted |
| `repositories/` | 0.68 GiB | 12% | Bare git mirrors of pinned deps | Identical across worktrees; git-relocatable |
| `checkouts/` | 0.23 GiB | 4% | Dep working copies | Needed, small; per-workspace |

## Investigation findings (2026-07-08, verified — not assumed)

1. **`index-build` is generated by the agents themselves.** The parent of every
   running `sourcekit-lsp` is a `claude` process — Claude Code is the LSP client.
   Each agent session that attaches to a worktree launches `sourcekit-lsp`, which
   (background indexing is default-on in the Swift 6.2 toolchain) does a
   prepare-for-indexing build into `.build/index-build/` — a full parallel
   SwiftPM build tree. Not the editor, not `swift build`.

2. **The running app is NOT in `index-build/`.** `scripts/restart.sh` builds and
   runs `.build/debug/TBD.app` = `arm64-apple-macosx/debug/` — the 2.0 GiB chunk
   we keep. Deleting `index-build/` cannot break a running or testable app.

3. **`.build` is NOT relocatable — cloning it is futile for the compiled bytes.**
   The build graph bakes the absolute worktree path everywhere: `index-build`'s
   own `debug.yaml` has **1,732** occurrences, its `build.db` **7,294**. A `cp -c`
   clone into a new worktree path is instant and block-shared, but the first
   build/index sees a graph pointing at the wrong worktree, treats every target
   as stale, and rebuilds — COW-diverging back to full size. Only the dep
   *sources* (`repositories/`, `checkouts/`) are path-independent.

4. **Archive already reclaims `.build`.** `WorktreeLifecycle+Archive.swift:165`
   calls `git.worktreeRemove(...)`, deleting the whole worktree incl. `.build`.
   The incident's dead weight was **un-archived idle** worktrees (11 of 14 never
   archived, some idle 7 weeks) — which a lifecycle/archive hook cannot catch.
   Reclamation must key off *idle time*, not lifecycle events.

5. **Web research: our GC approach is the community consensus, and no on-disk
   sharing exists for SwiftPM.** (a) There is no shared-`.build` recipe; "delete
   stale `.build` for idle checkouts" is the de-facto answer. (b) SwiftPM's
   `--enable-dependency-cache` (default on; global cache holds 679 MiB of bare
   mirrors) dedups the *fetch* but each `.build` still keeps its own full
   `repositories/` — it is npm-cache-style, **not** pnpm-style hardlink dedup;
   no tool links deps into a shared store surviving `swift package resolve`.
   (c) SourceKit-LSP background indexing can be turned off per-workspace via
   `.sourcekit-lsp/config.json` `"backgroundIndexing": false`. (d) The **only**
   technique that can dedup *compiled* bytes path-independently is SwiftPM
   **compilation caching with prefix-mapping over an LLVM CAS**, an active pitch
   on the new Swift Build engine — opt-in, early, parts uncacheable, not yet
   deployable. See Future Work.

## Approach chosen (and rejected alternatives)

**Chosen: suppress the biggest chunk at the source, and GC the rest on idle.**

- **Component A — idle-tiered GC** (`scripts/reclaim-build.sh`, launchd-driven,
  reads worktree activity from the `tbd` CLI read-only). Reclaims the path-baked
  debug build (Tier 2) and any surviving `index-build` (Tier 1) from idle
  worktrees. This is the only lever for the compiled bytes and the only thing
  that catches the un-archived idle tail.
- **Component B — launchd agent** running A hourly.
- **Component C — `index-build` suppression.** Seed a **gitignored**
  `.sourcekit-lsp/config.json` (`"backgroundIndexing": false`) into each active
  worktree so the 2.6 GiB is **never generated** — even actively-used worktrees
  stop paying it, which is what attacks the *burst* failure mode (many worktrees
  active at once during agent relaunches) that GC-after-idle alone cannot. Tier-1
  GC remains the backstop for `index-build` that predates the config or was built
  by an already-running LSP session.

Trade-off accepted for Component C: agents and any editor opened on a TBD
worktree lose **cross-file** LSP (workspace symbols, global find-references,
cross-module go-to-definition). **Live single-file diagnostics keep working.**
This is acceptable because agents navigate by grep/read (verified: the worktree
this was authored in did real agent work with no LSP attached and no `.build`),
and it is fully reversible (delete the gitignored configs). The config is
per-worktree, never committed — it must not disable indexing for other
contributors or the user's other Swift projects.

Rejected:

- **Reaper/suppression logic inside the TBD daemon.** TBD is an OSS product; a
  SwiftPM concern must not ship into every user's daemon. Dev tooling beside
  `restart.sh` / `test.sh`.
- **APFS-cloning the compiled `.build`.** Refuted by finding #3.
- **Shared SwiftPM dependency cache (dedup `repositories/`).** Refuted by finding
  #5b: SwiftPM offers no pnpm-style link, the only viable variant is fragile
  clone-on-worktree-create (needs a product-side create hook we're avoiding) for
  a 0.68 GiB gain that Tier-2 GC already reclaims on idle. Dropped as YAGNI.
- **A crash guardrail.** Descoped: steady-state footprint is the priority; a low
  baseline gives bursts headroom.

## Design

### Component A: `scripts/reclaim-build.sh` (the GC backbone)

Repo dev tooling, sibling to `restart.sh`. Not compiled, not in the daemon, not
shipped to product users. Source-guarded so its functions can be unit-tested by
`source`-ing it. Runnable by hand (`--dry-run` to preview) and by launchd hourly.

Responsibilities, in order:

1. **Enumerate worktrees from the source of truth.** Parse
   `tbd worktree list --json` (test seam: `RECLAIM_WT_JSON` fixture) for each
   worktree's `path`, `status`, and `liveClaudeSessionCount`. Only
   `status == "active"` worktrees are considered; archived ones are already
   reclaimed by `git worktree remove`.

2. **Per worktree with a `.build`, apply the safety gate then the tiers:**

   - **Hard skip (active build).** If any `swift-build` / `swift-frontend` /
     `swiftc` / `swift-driver` process references this worktree's path, leave the
     worktree untouched. (Test seam: `RECLAIM_PS_CMD`.)

   - **Tier 1 — `index-build/` only, aggressive (T1 = 6h).** If the newest file
     mtime under `.build/index-build/` is older than **6h**, delete just
     `index-build/`. Reclaims ~2.6 GiB with no runtime impact.

   - **Tier 2 — whole `.build`, relaxed (T2 = 48h).** If the newest file mtime
     under `.build/arm64-apple-macosx/` is older than **48h** AND
     `liveClaudeSessionCount == 0`, delete the entire `.build`.

   **Staleness is the newest *file* mtime within each tier's own subtree — never
   the `.build` directory mtime.** Tier 1's `rm index-build/` bumps `.build`'s
   dir mtime, so a `.build`-dir clock for Tier 2 would be perpetually reset by our
   own deletions. Measuring Tier 2 on `arm64-apple-macosx/` (Tier 1 never touches
   it) and Tier 1 on `index-build/` keeps the clocks independent.

   Tier 2 subsumes Tier 1 (deleting the whole `.build` removes `index-build` too);
   evaluate Tier 2 first.

3. **Report.** Log per-worktree actions and total bytes (via `df` delta on
   `/System/Volumes/Data`, never `du`). `--dry-run` prints the plan, deletes
   nothing. Fail-safe: on any CLI/`ps` error, skip that worktree, never delete on
   incomplete info. Idempotent.

Thresholds `T1`/`T2` are constants near the top, env-overridable
(`RECLAIM_T1_SECONDS`/`RECLAIM_T2_SECONDS`), defaulting to 21600 / 172800.

### Component B: launchd agent

A `LaunchAgents` plist, installed by `scripts/install-reclaim-agent.sh`, running
`reclaim-build.sh` **hourly**. Uninstall documented. Developer machine tooling —
not part of the shipped product.

### Component C: `index-build` suppression

On each run, `reclaim-build.sh` idempotently ensures every active worktree has
`.sourcekit-lsp/config.json` containing `{ "backgroundIndexing": false }` (only
writes if absent or lacking the key; never clobbers an existing customized
config). Combined with a committed `.gitignore` entry for `.sourcekit-lsp/`, this
keeps the file local to each worktree and out of the repo. New worktrees created
between hourly runs generate `index-build` until the next run seeds the config;
Tier-1 GC then reclaims that transient `index-build`. Over time the pair
converges each worktree to near-zero `index-build`.

Seeding does not retroactively delete an existing `index-build` (Tier-1 GC does)
and an already-running `sourcekit-lsp` picks up the config only on its next
init (new agent session) — both are handled by the GC backstop.

### Data flow

```
launchd (hourly)
  └─> scripts/reclaim-build.sh
        ├─ ensure .sourcekit-lsp/config.json (backgroundIndexing:false) in each active worktree   [Component C]
        ├─ tbd worktree list --json      (authoritative paths + status + live session count)
        ├─ ps -axo …                     (active-build guard)
        ├─ newest file mtime under index-build/ and arm64-apple-macosx/  (independent tier clocks)
        └─ rm -rf index-build/ | .build/  (guarded, tiered)
```

## Testing

- **Unit (shell, `source` the script, no live daemon):**
  - `newest_mtime` returns the newest file's epoch under a subtree; empty for
    missing/empty dir.
  - `has_active_build` matches a worktree path in fixture `ps` output only for
    `swift-*` build processes.
  - `plan_worktree` branch coverage: fresh `.build` (skip both), stale
    `index-build` only (Tier 1), stale whole `.build` no session (Tier 2), stale
    `.build` WITH live session (Tier 1 only, Tier 2 skipped), active-build match
    (hard skip), Tier-2 precedence over Tier-1.
  - `ensure_lsp_config` writes the config when absent, is a no-op when present,
    and never clobbers an existing config with other keys.
- **Integration (temp sandbox, real deletes):** build a fake worktree tree with
  planted mtimes + a fixture JSON; run without `--dry-run`; assert the right
  dirs are removed and others intact; `df`-measure reclaimed bytes.
- **Manual (documented):** `reclaim-build.sh --dry-run` on the live machine,
  eyeball vs `du -sh */.build`; then a real run with `df` before/after.

## Future work (fast-follow, tracked immediately after this ships)

**Pilot SwiftPM compilation caching (LLVM CAS + prefix mapping).** This is the
only known path to dedup the ~4.6 GiB *compiled* bytes across worktrees, because
prefix mapping canonicalizes on-command-line paths so "multiple instances of a
package at different file paths share cached outputs" — exactly our worktree
case. It rides the new Swift Build engine and is currently an opt-in pitch with
parts uncacheable. A dedicated research/spike should: confirm availability in the
pinned toolchain, measure real cross-worktree cache hit rates and disk behavior,
and assess concurrency safety of a shared CAS under bursty parallel builds. If
viable it could eventually *replace* Tier-2 GC for the compiled bytes. Sources:
`forums.swift.org/t/pitch-compilation-caching-support-in-swiftpm/88079`,
`github.com/swiftlang/swift-build`.

## Success criteria

- `.build` steady-state footprint stays at roughly (actively-building worktrees)
  × (~2.9 GiB — index-build suppressed, so the debug build + deps dominate),
  instead of N × 5.5 GiB; idle worktrees trend toward 0.
- No manual `du`/`rm` needed to keep the disk healthy.
- No active build, running app, or live agent session is ever disrupted.
