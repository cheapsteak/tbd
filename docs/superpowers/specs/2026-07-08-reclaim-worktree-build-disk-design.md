# Design: Reclaim worktree SwiftPM `.build` disk

*2026-07-08. Grounded in `~/projects/longeye-docs/disk-cleanup/tbd-swiftpm-build-lessons.md`
(the disk-full incident investigation) plus live measurement on this machine.*

## Problem

Every TBD worktree that builds the tbd Swift package produces a SwiftPM `.build/`
directory of **~5.5 GiB**, with **zero sharing** across worktrees (fully real,
`du`-honest bytes). Worktrees routinely outlive their sessions, so `.build` dirs
accumulate until hand-deleted. On this 460 GB machine that pool has hit 55 GiB
across 14 worktrees and driven the disk to near-0 free three times in ~5 weeks,
killing unrelated processes mid-write.

Cleanup today is manual (`du` + `rm`) and loses to normal usage within days.

**Goal:** keep the steady-state `.build` footprint low automatically, so the
developer never runs `du`/`rm` by hand. Crash prevention is a welcome side
effect, not the design target — steady-state reclamation is.

## Measured composition (identical across all live worktrees, 2026-07-08)

| Chunk | Size | % | What it is | Reclaim safety |
|---|---|---|---|---|
| `index-build/` | 2.6 GiB | 47% | SourceKit-LSP's **separate** background-index build | Disposable — nothing runtime reads it; regenerates on demand |
| `arm64-apple-macosx/` | 2.0 GiB | 37% | The real debug build (`debug/` symlinks into it; the running/testable app lives here) | Needed while active; one cold rebuild if deleted |
| `repositories/` | 0.68 GiB | 12% | Bare git mirrors of pinned deps | Identical across worktrees; git-relocatable |
| `checkouts/` | 0.23 GiB | 4% | Dep working copies | Needed, small; per-workspace |

## Investigation findings (2026-07-08, all measured on this machine)

These facts drive the design; each was verified, not assumed.

1. **`index-build` is generated by the agents themselves.** The parent of every
   running `sourcekit-lsp` is a `claude` process — Claude Code is the LSP client.
   Each agent session that attaches to a worktree launches `sourcekit-lsp`, which
   (background indexing is default-on in the Swift 6.2 toolchain) does a
   prepare-for-indexing build into `.build/index-build/` — a full parallel
   SwiftPM build tree (own `arm64-apple-macosx/`, `checkouts/`, `build.db`,
   `debug.yaml`). Not the editor, not `swift build`. This is why it correlates
   with worktree *use*, and why a worktree that only saw Read/Grep/Bash work has
   none.

2. **The running app is NOT in `index-build/`.** `scripts/restart.sh` builds and
   runs `.build/debug/TBD.app` = `arm64-apple-macosx/debug/` — the 2.0 GiB chunk
   we keep. Deleting `index-build/` cannot break a running or testable app.

3. **`.build` is NOT relocatable — APFS-cloning it is futile for the compiled
   bytes.** The build graph bakes the absolute worktree path in everywhere:
   `debug.yaml` has **1,732** occurrences of the worktree's absolute path,
   `build.db` has **7,294**. A `cp -c` clone into a new worktree path is instant
   and block-shared, but the first `swift build` / index sees a graph pointing at
   the wrong worktree, treats every target as stale, and rebuilds — COW-diverging
   every block back to full size. Only the dep *sources* (`repositories/` bare
   mirrors, `checkouts/`) are path-independent and shareable; the 4.6 GiB of
   `index-build` + debug build is fundamentally per-worktree.

4. **Archive already reclaims `.build`.** `WorktreeLifecycle+Archive.swift:165`
   calls `git.worktreeRemove(...)`, deleting the whole worktree dir incl.
   `.build`. The incident's dead weight was **un-archived idle** worktrees (11 of
   14 never archived, some idle 7 weeks) — which a lifecycle/archive hook cannot
   catch. This is why reclamation must key off *idle time*, not lifecycle events.

## Approach chosen (and rejected alternatives)

**Chosen (scope option 2): a standalone reclaimer script + a shared SwiftPM
dependency cache.**

- **Backbone — idle-tiered GC** via `scripts/reclaim-build.sh`, driven by
  launchd, reading worktree activity from the `tbd` CLI (read-only). This is the
  only lever that reclaims the path-baked 4.6 GiB (index-build + debug build) and
  the only thing that catches the un-archived idle tail.
- **Add-on — shared dependency cache** so the ~0.68 GiB `repositories/` mirrors
  aren't duplicated per worktree. Permanent baseline cut, composes cleanly with
  GC (deps live outside `.build`, so GC'ing `.build` doesn't evict them; a later
  cold rebuild re-fetches from the shared cache, no network, no re-dup). **Spec'd
  as a verify-first phase** (see its component) because SwiftPM cache/scratch
  semantics are explicitly unverified and must apply to every build invocation
  site.

Rejected:

- **Reaper logic inside the TBD daemon.** TBD is an OSS product other people
  install; a SwiftPM `.build` reaper is dev tooling for *this repo* (product
  users' worktrees may be Node/Rust/Go with entirely different bloat). It must
  not ship into every user's daemon runtime. It belongs beside `restart.sh` /
  `test.sh`.
- **APFS-cloning the compiled `.build` at worktree startup.** Refuted by finding
  #3 — non-relocatable, clone gets invalidated and rebuilt to full size.
- **Disabling SourceKit-LSP background indexing at the source** (scope option 3,
  descoped). It *would* prevent the 2.6 GiB rather than reclaim it, but the knob
  is a repo-level `.sourcekit-lsp/config.json` that turns background indexing off
  for **every** client — so a human opening the worktree in Xcode/VS Code/Zed
  loses cross-file LSP (workspace symbols, global find-references, cross-module
  go-to-definition), while live single-file diagnostics keep working. Since GC
  already reclaims `index-build` and its cost lands on the *editor* not the
  agents, we reclaim rather than suppress. Left as a future toggle if measurement
  shows agents never use cross-file LSP and editors never open these worktrees.
- **A crash guardrail** (disk-pressure watcher blocking new builds). Explicitly
  descoped: the priority is steady-state footprint; a low baseline gives bursts
  enough headroom.

## Design

### Component A: `scripts/reclaim-build.sh` (the GC backbone)

Repo dev tooling, sibling to `restart.sh`. Not compiled, not in the daemon, not
shipped to product users. Runnable by hand (with `--dry-run` to preview) and by
a launchd agent hourly.

Responsibilities, in order:

1. **Enumerate worktrees from the source of truth.** Parse
   `tbd worktree list --json` for each worktree's `path`, `status`, and
   `liveClaudeSessionCount`. Authoritative — avoids globbing a hardcoded dir (the
   CLI reports real paths, not always under `~/tbd/worktrees/tbd`) and yields the
   activity signal with no daemon code. Only `status == "active"` worktrees are
   considered; archived ones are already reclaimed by `git worktree remove`.

2. **Per worktree with a `.build`, apply the safety gate then the tiers:**

   - **Hard skip (active build).** If any `swift-build` / `swift-frontend` /
     `swiftc` / `swift-driver` process has this worktree's path in its args,
     leave the whole worktree untouched — deleting `.build` under a live build
     corrupts it.

   - **Tier 1 — `index-build/` only, aggressive (T1 = 6h).** If the newest file
     mtime under `.build/index-build/` is older than **6 hours**, delete just
     `index-build/`. Reclaims ~2.6 GiB (47%) with no runtime impact: `swift
     build`, running apps, and live single-file LSP diagnostics are unaffected;
     an agent session re-indexes in the background if it re-attaches. Primary
     lever — half the footprint, no rebuild cost — so it runs on a short timer.

   - **Tier 2 — whole `.build`, relaxed (T2 = 48h).** If the newest file mtime
     under `.build/arm64-apple-macosx/` (the real debug build) is older than
     **48 hours** AND `liveClaudeSessionCount == 0`, delete the entire `.build`.
     Reclaims the full compiled footprint; cost is one cold rebuild next time
     that worktree builds, so this catches only genuinely-abandoned worktrees.

   **Staleness is measured on the newest *file* mtime within each tier's own
   subtree — never the `.build` directory's own mtime.** Deliberate: Tier 1's
   `rm index-build/` bumps `.build`'s directory mtime, so a `.build`-dir clock for
   Tier 2 would be perpetually reset by our own Tier-1 deletions and never fire.
   Measuring Tier 2 on `arm64-apple-macosx/` (which Tier 1 never touches) and
   Tier 1 on `index-build/` keeps the two clocks independent and each reflective
   of genuine build activity.

3. **Report.** Log per-worktree what was reclaimed and total bytes (measured via
   `df` delta on `/System/Volumes/Data`, never `du`, per the incident doc).
   `--dry-run` prints the plan and skips all deletion.

Thresholds `T1`/`T2` are constants near the top (env-var overridable),
defaulting to 6h and 48h.

### Component B: launchd agent

A `LaunchAgents` plist (installed by a small `scripts/install-reclaim-agent.sh`,
or folded into the existing `scripts/install-hooks.sh` setup) that runs
`reclaim-build.sh` **hourly**. Uninstall documented. Developer machine tooling —
not part of the shipped product.

### Component C: shared SwiftPM dependency cache (verify-first)

Goal: the ~0.68 GiB `repositories/` bare mirrors (and, if safe, `checkouts/`) are
stored once in a shared location instead of duplicated per worktree.

**This component begins with a verification spike, and ships only if the spike
passes.** The spike must answer:

1. **Which mechanism actually eliminates the per-`.build` copy** — a shared
   `--cache-path`, a shared scratch/repositories location, or an env var. It is
   not enough to dedup the *fetch*; the per-worktree `repositories/` bytes must
   go away.
2. **Does it reach every build invocation site?** Not just the agent's `swift
   build` and `scripts/test.sh`/`restart.sh`, but crucially **sourcekit-lsp's own
   index-build**, which SwiftPM drives independently. A CLI flag we pass in one
   place won't cover sourcekit-lsp — the mechanism likely has to be an env var or
   a committed SwiftPM configuration that all clients honor.
3. **Is it concurrency-safe** under multiple worktrees building simultaneously
   (the observed failure mode is bursty parallel rebuilds)? `repositories/` (bare
   mirrors, read-mostly) is the safe candidate; per-workspace `checkouts/` may
   not be shareable and can stay per-`.build`.

If the spike shows no mechanism is both universal and concurrency-safe, **drop
Component C** — Component A already reclaims these bytes on idle (just not shared
permanently). Component C is a baseline optimization, never a correctness
dependency.

### Data flow

```
launchd (hourly)
  └─> scripts/reclaim-build.sh
        ├─ tbd worktree list --json      (authoritative paths + status + live session count)
        ├─ ps -axo …                     (active-build guard)
        ├─ newest file mtime under index-build/ and arm64-apple-macosx/  (independent tier clocks)
        └─ rm -rf index-build/ | .build/  (guarded, tiered)

(Component C, if it ships) all `swift build` / `swift test` / sourcekit-lsp
invocations honor a shared dep-cache location → repositories/ stored once.
```

### Error handling

- CLI / `ps` failures → skip that worktree (fail-safe: never delete on
  incomplete information), log a warning, do not abort the whole run.
- `rm` runs only after the gate + tier checks pass; a mid-run build starting is
  bounded by a per-worktree re-check immediately before delete.
- Idempotent — a second run finds nothing new to do.

## Testing

- **Unit-ish (shell, no live daemon):** feed the script a fixture
  `tbd worktree list --json` and a fake worktree tree with planted mtimes; assert
  in `--dry-run` mode that it selects exactly the expected Tier-1 / Tier-2 /
  skipped sets. Cover each branch: fresh `.build` (skip both), stale
  `index-build` only (Tier 1), stale whole `.build` with no session (Tier 2),
  stale `.build` WITH a live session (Tier 1 eligible, Tier 2 skipped), and an
  active-build process match (hard skip).
- **Component C spike (manual, documented):** with the shared-cache mechanism in
  place, build two worktrees and confirm (a) neither has a per-`.build`
  `repositories/` of its own, (b) an agent session's sourcekit-lsp index build
  also uses the shared cache, (c) two concurrent builds succeed. `df` before/after
  to confirm the baseline drop.
- **Integration (manual, documented):** run `reclaim-build.sh --dry-run` against
  the live machine, eyeball the plan vs `du -sh */.build`, then a real run with
  `df` before/after to confirm reclaimed bytes.

## Success criteria

- `.build` steady-state footprint stays at roughly (actively-building worktrees)
  × (~2.0–2.9 GiB, or less once Component C removes the shared `repositories/`),
  instead of N × 5.5 GiB.
- No manual `du`/`rm` needed to keep the disk healthy.
- No active build, running app, or live agent session is ever disrupted.
